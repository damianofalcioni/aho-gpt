# aho-gpt specification

## Product

The app name is `aho-gpt`, inspired by the Italian “Aho!” exclamation. The base application ID and Java namespace are `aho.gpt`; retain the `.wear` flavor and `.debug` build suffixes. Keep Android adapters under `aho.gpt.android` and protocol/session code independently JVM-testable.

Provide a lightweight Android, Android TV and Wear OS AI harness. Use Java, native Android APIs, no runtime dependencies, and the reference project's focused architecture and zero-violation complexity checks. Use vibe-navigator's black background, white iconography, rounded dark surfaces and outlined controls throughout the native UI. The main screen contains only a tappable app logo, which opens About & settings, and a large microphone/Speak button. Keep account, model, usage, permission, assistant, tool-rescan and sign-out controls on the separate About & settings page, alongside app information and help. Answers use a transient voice panel and overlay; no chat screen. Provide visible D-pad focus and layouts sized for phone, TV and watch screens.

## Voice and continuity

Use platform STT and TTS. Prefer on-device STT if available; clearly report missing providers. User invocation starts a microphone session. After answer playback, listen for up to eight seconds while the voice panel is foreground. A follow-up beginning in that interval retains context; otherwise start a fresh conversation. Keep history in memory, bound its size, and clear it after expiry, failure or lifecycle destruction. No wake-word or persistent background listener.

Provide a Speech languages entry in About & settings with independently saved STT and TTS language choices, each defaulting to the device language. Pass the chosen BCP 47 locale to recognition and playback. Show the requested recognition language by name and tag throughout acquisition, including follow-ups. Query ready STT languages from the same recognizer used for listening on Android 13 and later; query available TTS languages from the default playback engine. Capability queries must not open the microphone or download models. If a provider cannot report support, clearly label device-locale choices as unverified. Do not advertise downloadable STT languages as ready. Report missing or unsupported language data, preserve a visible answer on playback failure, and do not open follow-up listening after failed playback. TTS language changes the playback voice, not answer translation.

## OpenAI

Use only OpenAI models discovered from the authorized account. Authenticate using the documented Sign in with ChatGPT public-client flow, PKCE, state, nonce, signature validation, protected token storage and serialized rotating refresh. Request plan usage explicitly, enforce granted scope, and keep API keys out of the app. Provide the requested integrated WebView where supported, with a same-device system-browser fallback. Wear OS has no WebView; current sign-in requires a browser on the watch. Use public Responses with non-persistent streaming requests and explicit history. Only completed responses may trigger tools.

## Device capabilities

Scan all visible installed applications for accessible exported manifest intent filters and expose a searchable local catalog to the model. Support explicit activities, services and broadcasts, subject to Android permissions and execution restrictions. Do not claim extras' semantics or inaccessible capabilities can be inferred. Catalog metadata remains local until a search tool returns selected entries. Rescan explicitly and at process start.

Prioritize discovered app launchers in catalog search results and identify them explicitly. Opening an app by intent uses its discovered exported activity, MAIN action, phone or TV launcher category and launcher task flags. When a suitable launcher is found, invoke it directly without first hiding the voice activity or navigating Home. Return dispatch failures without claiming verified completion; Android background-launch restrictions still apply.

Supplement manifest parsing with public package-resolver queries for phone/TV launchers and general HTTP/HTTPS handlers, including split APK activities. Do not claim complete discovery of other split-manifest filters. Expose two device-tool functions, or four when accessibility is available, with at most 25 selected catalog entries per search page; keep the full inventory local.

Extend the discovery function with an on-demand overview of available standard-action categories, declaration counts and distinct-app counts, without app identities or individual capability IDs. Support structured AND filters for app name, exact package, category, component kind, action, URI scheme and MIME type, including wildcard MIME matching. Rank exact app matches ahead of substring matches and prefer launchers within equal relevance; preserve keyword search and pagination. Instruct the model to use the overview for unfamiliar abilities and targeted filters for known goals, and to narrow or paginate before claiming a capability is absent.

Describe each result with its standard category, meaning, usage limits and whether its semantics are known. Derive descriptions only from documented standard Android activity contracts; keep custom and non-activity intent semantics unknown. Describe declarations rather than guaranteed outcomes. Explicitly report unsupported image-stream extras, URI grants and returned camera/document data. Discovery must not change execution permissions, argument validation or cancellation behavior.

When the app's accessibility service is enabled, include screen-reading and requested UI action tools. Exclude password nodes; treat other screen text and app metadata as untrusted input. No passive event retention or key interception. Mutating tools carry out the active spoken request and return actual dispatch results; unclear targets must be clarified by voice.

Validate tool arguments locally against their advertised schema, including exact names, types, enums, required fields and size limits. Reject duplicate JSON keys, trailing data and unsupported syntax before execution. Give each recognized spoken turn its own cancellable, two-minute execution scope, independent of conversation continuity. Check authority after model responses and immediately before tools, including on the execution thread for queued Android work. Closing the panel revokes the scope; already dispatched external actions cannot be undone. Ignore callbacks from retired requests.

Keep the eight-round tool loop and additionally cap each turn at 64 distinct call IDs. Cache receipts per turn: identical encoded calls with the same ID return the existing receipt, and changed calls reusing an ID are refused. New IDs are not semantically deduplicated; instruct the model not to bypass replay protection or repeat uncertain mutations. Report mutation outcomes as refused, rejected, accepted or unknown with explicit dispatch evidence and no claim of verified task completion. Unexpected execution exceptions use fixed codes. After UI actions invalidate cached screen nodes. These controls enforce local execution contracts, not independent semantic verification of the spoken request.

Instruct the model to try enabled accessibility tools when targeted intent searches yield no usable capability or intent dispatch reports a failure. The fallback may find and open the requested app through Home, its launcher or Recents, as well as navigate inside it, within the same clear spoken request. Require fresh screen reads after navigation, node IDs from the latest read and a visible-target check after opening an app. Respect platform permissions and inaccessible controls; clarify ambiguous targets and report unavailable or failed fallback without claiming success. Keep the existing bounded tool loop; this policy is model guidance rather than a deterministic execution guarantee.

## Form factors

One Android application module with shared sources and `handheld` (phone/TV) and `wear` flavors. Native layouts must work with touch, D-pad and round screens. Expose `aho.gpt.android.ui.VoiceActivity` and voice-command intents for a separate TV button mapper. Support default-assistant selection through the exported `ACTION_ASSIST` activity on devices exposing the system picker. The system assistant shortcut opens the voice panel and starts listening after setup and microphone permission. Use the installed speech provider; do not register a voice interaction or recognition service that replaces it. No wake word, lock-screen assistant integration or built-in global key mapper. Answer overlays can use an enabled accessibility service or a separately granted overlay permission; voice works without either.

## Validation

Use PMD with the inherited reference limits, plain JVM unit tests for protocol/session safety, lint for both variants, and debug/release builds with release shrinking. Explicitly distinguish static/build verification from physical-device integration testing. Maintain zero runtime dependencies.
